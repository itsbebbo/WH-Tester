## 1. Purpose and Scope

This tester monitors a board under test (BUT) outputs to indicate the status of those outputs. The BUT has two independent outputs, one intenal and one external. The two outputs are tested separately and selected as separate operating modes on the tester:

- **Internal Connector BUT**: The BUT provides 3 digital outputs, power on, arm and fire which are to be displayed as indicators on screen. The tester will provide two outputs called 'red error' and 'green status' which will be driven by the power on, arm and fire inputs using a state machine.

- **External Connector BUT**: The BUT provides a single output which the tester will either drive open circuit (no device connected), closed circuit (short circuit error), 0.22ohms (calibration) or 1 ohm (device connected) using digital outputs from the tester. When the 1 ohm is connected the tester measures the current provided from the BUT using an INA219 current sensor. This value will be displayed and when over 1200mA will be classed as a correct active output. Lower than this value will be displayed as inactive.

The tester will also be able to simulate a BMP280 to provide air or ground barometric pressures over I2C.

The tester will also provide a serial output to send MCP commands to command the BUT for ARM and FIRE.

The tester itself never applies power to a real igniter, squib, or other energetic device — all "arm"/"fire" actions are serial commands to the BUT, and all feedback is measured/read back from the BUT, not generated by the tester.

Out of scope for this document: the design of the board under test, and the definition of pass/fail limits for its outputs (these depend on the BUT's own specification, to be supplied separately).

## 2. System Overview

```
 ┌───────────────────────────┐        Serial (UART, TBC)        ┌───────────────────────┐
 │      M5Stack CoreS3        │ ───────────────────────────────► │   Board Under Test     │
 │  (this tester)              │ ◄─────────────────────────────── │   (internal or external│
 │  LVGL UI, INA219, GPIO in  │   Digital status in (internal)   │    output variant)      │
 └───────────────────────────┘   Current loop in (external)     └───────────────────────┘
```

- The tester is the master: it issues arm/fire commands to the BUT over serial and independently observes the BUT's real-world outputs.
- **Internal mode**: observation path = digital GPIO inputs on the CoreS3, one per BUT status line (power/arm/fire — exact count and mapping TBC, pending the BUT's I/O list).
- **External mode**: observation path = INA219 current sensor wired into the BUT's current-loop output.
- A shared "fire activated" event (however it is detected) triggers a full-screen flash and a short audio cue on both screens.

## 3. Hardware Platform

### 3.1 M5Stack CoreS3 (confirmed specification)

| Item | Detail |
|---|---|
| MCU | ESP32-S3, dual-core Xtensa LX7 @ up to 240 MHz, 8 MB PSRAM, 16 MB flash |
| Display | 2.0" IPS, 320×240, capacitive touch (FT63X6 touch controller) |
| Audio out | AW88298 I2S amplifier driving a 1 W onboard speaker |
| Power mgmt | AXP2101 PMU; LCD reset/backlight and some peripheral power rails are switched via the AW9523 I/O expander, not raw GPIO |
| Internal I2C | GPIO12 (SDA) / GPIO11 (SCL) — PMU, touch, IMU, IO expander. **Not to be used for the INA219.** |
| Grove Port A | External I2C — GPIO2 (SDA) / GPIO1 (SCL). Proposed home for the INA219. |
| Grove Port B | GPIO8 / GPIO9 — free GPIO |
| Grove Port C | GPIO17 / GPIO18 — free GPIO, usable as UART |
| M5-Bus (bottom connector) | Breaks out the remaining GPIO for use with a base/breakout module — required if more than the two Grove ports' worth of digital I/O is needed |

**Open item:** the CoreS3 alone only exposes two Grove ports' worth of free GPIO (4 pins total) plus a UART-capable pair. If the internal-mode BUT has more than ~2 status lines to monitor, a base module (e.g. one of M5Stack's DIN/proto bases) exposing the M-Bus GPIO will be needed. Please confirm the BUT's I/O count so the correct base can be specified.

### 3.2 INA219 current sensor (Adafruit board, default configuration as specified)

| Item | Detail |
|---|---|
| Interface | I2C, default address **0x40** (A0/A1 unpopulated) |
| Shunt | Default onboard 0.1 Ω |
| Library | Adafruit_INA219 (Arduino) |
| Key calls | `begin()`, `setCalibration_32V_2A()` (or `_16V_400mA()` for finer resolution — TBC, depends on the BUT's expected current range), `getCurrent_mA()`, `getBusVoltage_V()`, `getPower_mW()` |
| Wiring | VIN+/VIN− in series with the BUT's current-loop output; SDA/SCL to Grove Port A |

**Open item:** the expected current range of the external-mode BUT output isn't yet specified. With the default 0.1 Ω shunt, `setCalibration_32V_2A()` gives coarse resolution over the full ±2 A range; `setCalibration_32V_1A()` or `_16V_400mA()` give finer resolution over a smaller range. Please confirm the BUT's nominal/expected output current so the calibration constant can be selected correctly — this is not a placeholder that should be guessed.

### 3.3 Serial link to BUT

Proposed: hardware UART on Grove Port C (GPIO17/18), keeping the USB/console UART (GPIO43/44) free for debug logging during development.

**Open item — protocol not yet defined.** Needs from you: baud rate, framing (fixed-length vs. delimited vs. a framed/CRC protocol as used on your prior ESP32 UART work), command set for arm/fire/status-request, and whether the BUT is polled or sends unsolicited status. Nothing below assumes a specific protocol — the UI/state machine is written against abstract "send arm", "send fire", "status received" events.

## 4. Software Architecture

- **Framework**: Arduino + M5Unified/M5CoreS3 board support (for display, touch, speaker, power management) with **LVGL** as the graphics library, ported onto M5GFX as the display driver.
- **Structure**: single LVGL screen per major state (Home, Internal, External), switched with `lv_scr_load()`. Each screen is a self-contained widget group with its own update callback driven by a periodic status-poll timer (`lv_timer`).
- **Serial handling**: run on core 0 as a dedicated task (FreeRTOS), decoupled from the LVGL/UI task on core 1, communicating via a queue — avoids UI stutter or missed serial bytes during touch handling.
- **Fire-event handling**: implemented as a single shared function (`trigger_fire_alert()`) called from either screen's status-update logic, so the flash+sound behaviour is defined once, not duplicated.

## 7. Screen 3 — External Tester

| Element | Type | Behaviour |
|---|---|---|
| Mode selector | 3-way switch/segmented control | Calibration / Open Circuit / Test Fire — sent to the BUT as the active test mode |
| Output power | Text label, live-updating | Displays `getCurrent_mA()` from the INA219, formatted as e.g. `123.4 mA` |
| Fire activated indicator | LED-style icon | Set from a rule based on measured current (TBC — see below) or from a BUT status message if one exists in the serial protocol. On activation: triggers full-screen flash + boom sound (§9) |

**Open item:** for the external variant, how is "fire activated" actually detected? Options:
(a) the BUT sends an explicit status byte/message over serial, or
(b) the tester infers it from the INA219 reading crossing a threshold.
These have different reliability characteristics and need your decision before the detection logic can be specified.

**Calibration mode**: needs a definition of what's being calibrated — INA219 zero/gain calibration, or establishing a per-unit expected-current baseline for later pass/fail comparison in Test Fire mode. Please confirm which.

**Open Circuit mode**: presumed to check for a BUT output current near zero (loop open) as a pre-fire continuity-style check, analogous to a continuity test but read via the INA219 rather than a dedicated ohmmeter function. Confirm this interpretation is correct.

## 9. Shared "Fire Activated" Alert Behaviour

Applies identically on both test screens:

1. Fire-activated condition detected (per §6/§7 detection logic).
2. Screen briefly flashes (e.g. white or red overlay for ~150–250 ms — exact duration/colour TBC, your call).
3. A short "boom" sound plays via the onboard speaker (AW88298 amp, `CoreS3.Speaker`).

**Open item — audio asset**: the M5Unified Speaker class plays raw PCM buffers directly (`Speaker.playRaw()`) or simple tones (`Speaker.tone()`) natively; playing a compressed file (MP3/WAV) needs either pre-converting the sound to a raw PCM array baked into flash, or pulling in a decoder library (e.g. ESP8266Audio) if you want to play from an SD card file at runtime. Please confirm which approach you want and supply (or approve sourcing) the actual sound asset — no placeholder sound should be assumed without your sign-off, per your note about not inventing unreferenced results.
